## Code of Conduct

### Our Standards

**Examples of behavior that contributes to a positive environment:**
- Using welcoming and inclusive language
- Being respectful of differing viewpoints and experiences
- Gracefully accepting constructive criticism
- Focusing on what is best for the community
- Showing empathy towards other community members

**Examples of unacceptable behavior:**
- The use of sexualized language or imagery
- Trolling, insulting/derogatory comments
- Personal or political attacks
- Public or private harassment
- Publishing others' private information without explicit permission

## Getting Started

### Prerequisites

- Basic understanding of AI-assisted development
- Familiarity with markdown documentation
- Experience with iterative development processes

### Fork and Clone

```bash
# Fork the repository on GitHub
git clone https://github.com/your-username/hello-dev.git
cd hello-dev
```

### Directory Structure

```
hello-dev/
 SKILL.md # Framework definition and execution contract (authoritative entry)
 modules/
 index.md # Module index (auto-regenerated by gen-index.js, do not edit manually)
 core/ # Core modules (authoritative)
 state-protocol.md # State persistence protocol
 approval/git-gate.md # Git risk classification (authoritative basis for hooks)
 task/classifier.md # Task classification
 stages/ # Stage definitions (authoritative)
 paths/ # Execution paths (authoritative)
 hooks/
 git-gate.js # Git approval gate (PreToolUse hook)
 test-git-gate.js # Gate unit tests
 scripts/
 state.js # State file read/write / recovery / diff reports
 gen-index.js # modules/index.md regeneration
 check-links.js # Markdown broken link check
 sync-to-codex.sh # (removed in open-source version)
 docs/progress_coding/ # Development process doc rules
 templates/ # Document templates
 references/ # Reference materials
 skills/ # Bundled collaboration skills
```

> Note: This is the open-source version. The original project includes additional directories
> (`archive/`, `expert-packages/`, `.workbuddy/`) that are not part of this distribution.
> In case of conflict, refer to the "Authority" table in `SKILL.md` and `modules/index.md`.

## Development Workflow

### Execution and validation contract

Follow [SKILL.md](SKILL.md), the [state protocol](modules/core/state-protocol.md), and [append-only log rules](docs/progress_coding/_RULES.md). Add behavioral regressions for state changes, including rejected writes and recovery. Record changes immediately, not only at release time.

Run `bash scripts/self-check.sh` after relevant edits; regenerate the module index with `node scripts/gen-index.js` when module descriptions change. The checker is a bounded regression suite, not proof of host hook registration or a complete security audit.

State CLI transitions now require explicit completion/start, current-attempt evidence and submitted module approval with a reason. Older workflows relying on implicit completion must follow the updated protocol. Installed-copy synchronization remains separately authorized; see [runtime boundaries](references/runtime-adapters.md).

### Version Numbering

Hello Dev uses Semantic Versioning (SemVer):

```
major.minor.patch

Example: v15.1.0
- Major (15): Breaking changes to core flow
- Minor (1): New features, patterns, or stages
- Patch (0): Bug fixes, documentation updates

Actually released versions follow git tags (`git tag -l`); historical zip packages have been moved to `archive/`.
```

### Version Update Rules

| Change Type | Version Bump | Examples |
|------------|-------------|----------|
| Breaking changes | Major | Removing a stage, changing D-S-C pattern |
| New features | Minor | Adding a new stage, new pattern category |
| Bug fixes | Patch | Fixing incorrect instructions, improving clarity |

### Change Categories

#### 1. Documentation Changes (Patch)

- Fixing typos or grammar
- Clarifying existing instructions
- Improving examples
- Updating links

#### 2. Pattern Changes (Minor)

- Adding new patterns
- Updating existing patterns
- Adding pattern examples
- Expanding pattern index

#### 3. Stage Changes (Minor or Major)

- Adding new stage
- Modifying stage flow
- Adding new teaching elements
- Changing core patterns

#### 4. Core Changes (Major)

- Changing the loop structure
- Removing existing features
- Changing fundamental principles
- Version incompatible changes

---

### Pre-commit Checklist

```bash
bash scripts/self-check.sh
```

It validates syntax, broken documentation links, index drift, risk table and hook consistency, documentation command authenticity, dead fields and state protocol.
**Do not commit if any check fails** -- these checks exist because "documentation claims X, implementation does Y" drift is inevitably missed by human review.

## Documentation Guidelines

### File Naming

| Document Type | Naming Convention | Example |
|-------------|------------------|---------|
| Stage docs | `stage-{number}-{name}.md` | `stage-4-architecture.md` |
| Core docs | `_{name}.md` | `_memory-matrix.md` |
| Templates | `{name}.md` | `requirement-doc.md` |
| Patterns | `pattern-{name}.md` | `pattern-result-type.md` |

### Frontmatter Format

All markdown files should include frontmatter:

```markdown
---
name: {unique-name}
description: {one-line summary}
category: {category}
layer: {L0-L4 or N/A}
version_added: {vX.Y}
---

# Document Title

Content...
```

### Documentation Standards

1. **Clarity**: Write for clarity, not impressiveness
2. **Completeness**: Include all necessary information
3. **Consistency**: Follow existing patterns and style
4. **Correctness**: Verify all claims and examples

### Content Guidelines

**DO:**
- Use active voice
- Include concrete examples
- Reference other documentation
- Break complex topics into sections
- Use consistent terminology

**DON'T:**
- Use jargon without explanation
- Include contradictory information
- Leave TODO items without context
- Make unsupported claims

## Pattern Contributions

### When to Add Patterns

Add a new pattern when:
- A solution worked well across multiple loops
- The pattern is reusable in different contexts
- The pattern has a clear name and definition
- Examples demonstrate the pattern

### Pattern Template

```markdown
---
name: pattern-{name}
description: {brief description}
category: {design/teaching/process/decision/testing}
layer: L3
---

# Pattern: {Name}

## Purpose

[What problem this pattern solves]

## When to Use

[Conditions for applying this pattern]

## How It Works

[Step-by-step explanation]

## Example

```
[Code or workflow example]
```

## Why It Works

[Explanation of effectiveness]

## Related Patterns

- [[pattern-name]]: [relationship]

## Anti-Pattern

[[anti-pattern-name]] - [what to avoid]
```

### Pattern Categories

| Category | Description | Examples |
|----------|-------------|----------|
| Design | Software architecture patterns | Component Design, Service Layer |
| Teaching | Learning and explanation patterns | Progressive Disclosure, Analogy |
| Process | Workflow patterns | D-S-C, Ask-Option-Decide |
| Decision | Decision-making patterns | First Principles, Five Whys |
| Testing | Testing strategies | Risk-Based, Boundary Testing |

## Versioning

### Changelog Format

```markdown
## [vX.Y.Z] - {Date}

### Added
- New feature description
- New pattern category

### Changed
- What changed and why
- Migration instructions if needed

### Deprecated
- What will be removed in future
- Replacement recommendation

### Removed
- What was removed
- Why it was removed

### Fixed
- Bug fix description
- Related issue number

### Security
- Security improvements
- Vulnerability fixes
```

### Version Compatibility

- Always maintain backward compatibility within major version
- Document breaking changes prominently
- Provide migration paths when possible

## Release Process

### Release Checklist

```markdown
## Release Checklist - vX.Y.Z

### Pre-Release
- [ ] All changes documented in changelog
- [ ] Documentation reviewed and updated
- [ ] Pattern index updated
- [ ] SKILL.md version updated
- [ ] No breaking changes without major version bump

### Testing
- [ ] Tested with sample loops
- [ ] All examples verified working
- [ ] Links checked and valid
- [ ] Cross-references verified

### Announcement
- [ ] Changelog updated
- [ ] Release notes prepared
- [ ] Community notified
```

### Release Frequency

| Version Type | Frequency | Rationale |
|-------------|-----------|-----------|
| Patch | As needed | Bug fixes, documentation improvements |
| Minor | Monthly | New features, patterns, improvements |
| Major | Quarterly | Breaking changes, major refactoring |

## Pull Request Process

### PR Template

```markdown
## Description

[Brief description of changes]

## Type of Change

- [ ] Bug fix
- [ ] New feature
- [ ] Documentation update
- [ ] Pattern addition
- [ ] Refactoring

## Checklist

- [ ] Changes follow naming conventions
- [ ] Frontmatter included
- [ ] Documentation updated
- [ ] Pattern index updated (if applicable)
- [ ] Examples verified

## Related Issues

[Link to related issues]
```

### PR Review Criteria

1. **Correctness**: Does it work as intended?
2. **Clarity**: Is it clearly written?
3. **Consistency**: Does it match existing style?
4. **Completeness**: Is all necessary information included?
5. **Compatibility**: Does it break existing functionality?
