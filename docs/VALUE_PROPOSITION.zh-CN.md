# Hello Dev 价值主张

## 核心定位

**AI 代理的治理层** -- 不仅仅是开发治理框架，而是 AI 代理的操作系统级基础设施。

**标语**：确保 AI 构建你真正想要的东西。

## 差异化：交付用户真正想要的

不同于其他 AI 开发工具关注"更快地写代码"，Hello Dev 关注**构建正确的东西**。通过结构化的需求拷问、原型优先验证、以及每个关键阶段的强制用户检查点，确保最终交付物匹配用户的真实需求 -- 而不是 AI 猜测的结果。

| 传统 AI 开发工具 | Hello Dev |
|-----------------|-----------|
| 关注编码速度 | 关注交付正确性 |
| 假设需求是清楚的 | 假设需求需要验证 |
| 开发完了再验证 | 开发之前就验证 |
| "我写得很快" | "我构建了正确的东西" |

### 确保正确性的三大机制

**1. 结构化需求拷问（grill-me）**

不是"告诉我你想要什么"，而是引导式的决策树遍历：
- 每个问题都有推荐答案（用户只需确认或修改）
- 问题根据之前的回答动态调整（动态的，不是静态的）
- 每个决策都被记录，形成完整的决策链路

**2. 原型验证前置**

在 Hello Dev 的 15 阶段流程中，Prototype 阶段在 Implementation 之前：
- 用户可以在写代码之前看到可交互的原型
- 提前发现"这不是我想要的"
- 在设计阶段修改成本极低，在开发阶段修改成本极高

**3. 强制用户检查点**

用户在关键节点被明确邀请参与：
- Requirement：确认需求规格
- Feature Design：确认功能设计
- Architecture：确认架构方案
- Prototype：验证原型交互
- Review：最终确认

这些参与点不是"可选的"，而是**流程强制的**。跳过了就无法继续。

## 五大维度

### 1. 开发治理框架（表层）

| 传统开发 | Hello Dev | 本质变化 |
|----------|-----------|----------|
| 需求靠默契 | 需求靠契约 | 减少理解偏差导致的返工 |
| 架构决策在黑箱里 | 架构决策可回溯 | 减少"为什么这样设计"的重复讨论 |
| 测试是最后跑一遍 | 测试是风险驱动的证明 | 减少"测试通过但实际有 bug"的遗漏 |
| 返工是隐性成本 | 返工是可量化的数据 | 让团队能回答"我们犯了多少错" |
| 经验靠写 Wiki | 经验是开发副产品 | 让经验积累不再依赖"额外工作" |
| 多文件修改靠祈祷 | 多文件修改靠依赖图 | 减少合并冲突和覆盖事故 |
| 开发日志是额外负担 | 开发日志是审计追踪 | 让未来的自己能理解过去的决策 |

### 2. AI 代理操作系统（中层）

| 人类世界 | Hello Dev 世界 |
|----------|---------------|
| 操作系统（Linux/Windows） | Hello Dev 状态机 |
| 进程 | AI 代理会话 |
| 权限系统（sudo/rbac） | 双闸门（git-gate + opsgate） |
| 日志系统（syslog/journal） | `.hello-dev/state.json` + 开发日志 |
| 进程间通信 | 波次调度 + 文件冲突检测 |
| 检查点/恢复（checkpoint/restore） | `resume` + 阶段回滚 |
| 审计追踪（audit trail） | 证据链 + 记忆系统 |

**类比**：Linux 不是"一个应用程序"，而是"所有应用程序的运行环境"。Hello Dev 也不是"一个开发工具"，而是"AI 代理的运行治理环境"。

### 3. 经验积累基础设施（深层）

五层记忆 + 证据链解决的不只是"记住做了什么"，而是：

- **记住什么有效、什么失败了**（`improved` / `regressed` / `no_effect`）
- **拒绝记录推测和噪音**（write gate 拒绝"可能"、"大概"、"临时方案"）
- **跨会话召回**（Bootstrap 阶段自动检索相关记忆）

**价值**：组织级 AI 经验的积累载体 -- 不只是"这个代理上次怎么做的"，而是"这个团队所有代理在所有项目中验证过的经验"。

### 4. 多代理协调协议（协作层）

波次调度 + 文件冲突检测 + 子代理约束，本质上是一个**多代理协调协议**。

适用场景不限于"写代码"：

- **多代理研究报告**：代理 A 搜数据、代理 B 写分析、代理 C 做可视化 -- 不能互相覆盖
- **多代理内容生产**：代理 A 写文案、代理 B 配图、代理 C 排版 -- 文件边界不能冲突
- **多代理数据处理**：代理 A 清洗数据、代理 B 转换格式、代理 C 生成报告 -- 依赖顺序必须正确

### 5. AI 行为合规基础设施（合规层）

当 AI 代理开始在生产环境中执行操作（部署、数据库变更、API 调用），**谁为这些操作负责？**

Hello Dev 的 `stepDigest` 机制提供了答案：

> 每一步操作都绑定了一个不可变的执行意图（命令 + 环境 + 目标 + 源文档 + 风险结论），任何变更自动使审批失效。审批有 TTL，过期自动失效。审批是谁批准的、什么时候批准的、基于什么信息批准的 -- 全部可追溯。

**价值**：法律合规基础设施 -- 当监管机构问"这个 AI 操作是谁授权的"时，Hello Dev 能给出精确答案。

## 开发增强维度

### 需求工程

| 传统开发 | Hello Dev | 本质变化 |
|----------|-----------|----------|
| 需求确认靠猜测 | 需求确认靠决策树遍历 | 减少"我以为你要的是这个"的返工 |

**机制**：`grill-me` 技能把需求确认变成结构化决策树遍历：
- 每个问题有推荐答案（不是开放式提问）
- 每个分支有取舍说明
- 一次一问（不是 30 点问卷）
- 产出完整决策树（不是模糊需求文档）

### 软件工程纪律

| 传统开发 | Hello Dev | 本质变化 |
|----------|-----------|----------|
| 软件工程靠自律 | 软件工程靠可执行的纪律 | 让模块化、单一职责等原则真正落地 |

**机制**：阶段体系和模块分解把软件工程原则变成可执行纪律：
- **模块化**：每个子任务有明确的 `affectedFiles`，模块边界在任务分解时定义
- **单一职责**：每个阶段有明确职责（Requirement 只确认需求，Architecture 只定架构）
- **依赖倒置**：波次调度强制定义任务依赖关系
- **接口隔离**：每个模块的输入输出在 Architecture 阶段定义

### 质量保障

| 传统开发 | Hello Dev | 本质变化 |
|----------|-----------|----------|
| 测试是最后跑一遍 | 测试是风险驱动的证明 | 减少"测试通过但实际有 bug"的遗漏 |
| 代码审查是事后补救 | 代码审查是过程中持续验证 | 问题在早期就被发现 |
| 技术债务是隐形负担 | 技术债务是可追踪的待办项 | 让"以后再说"变成"现在记录、定期回顾" |

### UI/UX 设计

| 传统开发 | Hello Dev | 本质变化 |
|----------|-----------|----------|
| UI/UX 设计靠拍脑袋 | UI/UX 设计靠设计令牌和组件规格 | 减少"这个按钮应该多大"的反复讨论 |
| 原型验证靠开发完再改 | 原型验证靠先验证再开发 | 减少"开发完了才发现方向错了"的返工 |
| 设计系统是文档 | 设计系统是可执行的规范 | 减少设计和代码之间的空隙 |

**机制**：`ui-ux-pro-max` 技能提供基于证据的设计决策：
- **设计令牌（Design Tokens）**：颜色、字体、间距标准化为可复用变量
- **组件规格（Component Specs）**：每个 UI 组件有明确规格说明
- **布局蓝图（Layout Blueprint）**：页面布局在开发前定义
- **实现指引（Implementation Notes）**：设计决策有明确技术实现指引

**Prototype 阶段**：在 Implementation 之前产出可运行的 HTML 原型，用户可直接操作验证。

## 一句话总结

**Hello Dev 对开发本身的增强，不是让代码写得更快，而是让开发过程中的每一个决策都可追溯、可审计、可学习。它把开发从"凭经验的艺术"变成了"有证据的工程"。**

## 开源定位建议

不要只说"开发治理框架"。说"**AI 代理的治理层**" -- 开发只是第一个被验证的场景，不是唯一场景。

核心价值主张：

> **让不可信的自主执行体（AI 代理）变成可审计的工程实践。**
